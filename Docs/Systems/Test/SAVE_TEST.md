# SAVE_TEST

로컬 저장과 수동 백업의 설정/검증 절차입니다. 저장·백업 개편은 완료했으며 확인 결과는 아래 최신 기록에 둡니다. 현재 계약은 [SAVE_SYSTEM.md](../SAVE_SYSTEM.md), 별도 UI 연계·추가 검증·보류 항목은 [TODO.md](../../TODO.md#firebase-수동-백업복원)에 둡니다. 아래 절차를 적었다는 사실만으로 검증 완료를 의미하지 않습니다.

## 2026-10-30 저장소 분리 확인

개편 후 로컬 저장·불러오기와 버전 8 JSON 검증 완료. 저장 실패 시 기존 진행 유지, 재시도와 복원 전 원본 보관을 확인했습니다.

### 백업 버전 보호 보완

백업 권한 오류 해결과 정상 동작 확인. 최신 백업 보호와 취소·종료 처리는 격리 검사로 확인했습니다.

이번 저장 개편은 완료했습니다. 다른 담당 연계 후 전체 흐름 확인과 필요 시 추가 검증은 [TODO](../../TODO.md#firebase-수동-백업복원)에 구분해 둡니다. 버전 정책은 [저장 계약](../SAVE_SYSTEM.md#저장소-연결-계약)을 따릅니다.

## 씬 연결

| 대상 | 설정 |
| --- | --- |
| 공통 관리자 프리팹 | GameBootstrap으로 자동 생성. 씬에 GameManager/SaveManager 별도 배치하지 않음 |
| 프리팹의 SaveManager | 기존 CurrencyData와 Firebase/데이터 맵 설정 유지 |
| TestScene | 기존 모듈/설정 참조 유지. 수동 검증은 Auto Begin Stage 끄기 |
| 최고 별 검증 | Mission Map Id와 Mission Difficulty 확인 |

싱글턴 등록과 씬 간 유지는 GameManager가 담당합니다. Play 중 생성된 공통 관리자의 SaveManager를 선택해 검증합니다. Inspector에서 저장 슬롯을 선택하지 않으며 현재 파일은 `Application.persistentDataPath/Saves/slot_0.json`입니다. 기존 진행을 보존하려면 Play를 끄고 저장 폴더 복사본을 별도로 보관합니다.

## 첫 타이틀 진행 준비

코드 반영과 정적 확인을 마쳤습니다. 아래 Unity 플레이 검증은 남아 있습니다.

| 조건 | 확인할 결과 |
| --- | --- |
| 기존 저장 / 빈 슬롯 | 타이틀에서 로비를 열기 전에 진행 준비. 기존 값 유지 또는 신규 파일과 최초 재화 1회 반영. 로비 열기·닫기·재진입 시 파일 재읽기 없이 확정 진행 사용 |
| 손상·미지원 / 쓰기 실패 | 시작 거절, 실패 사유 제공, 원본 보존. 원인 해소 후 TryRetryStartupProgress로 진행만 다시 준비 |
| 설정 실패 / 테스트 씬 직접 실행 | 설정 실패와 별개로 진행 준비. PlayerTest 직접 시작과 BackupTest Inspector 경로 유지 |

저장 파일 변경은 검증용 복사본에서 수행합니다. 로비 요청은 기존 LobbyDebugInspector를 사용하며, 타이틀 상태 표시와 재시도 버튼을 거치는 검증은 LHJ 연동 후 수행합니다.

## 디버그 사용

Play 중 TestScene Inspector 상단의 저장 검증을 사용합니다. 진행 관리, 도전/미션/도감, 상점/해금/강화, 플레이어/동료/전투 대상, 재화/보상 추가 검증은 필요할 때 펼칩니다. 플레이 중 씬 설정은 읽기 전용입니다.

| 조작 | 확인하는 것 |
| --- | --- |
| 전체 진행 저장 | 기존 저장 API 결과. 성공 후 자동 전체 조회하지 않음 |
| 전체 저장값 조회 | 확정 데이터의 재화/수량/단계/해금/선택/미션/도감/최고 별 요약 |
| 진행 관리의 씬 재초기화 | 파일 읽기 없이 공유 진행으로 모듈 재연결 |
| Play 종료 후 재실행 | 실제 파일에서 진행 복원 |

조회는 현재 확정 진행을 기준으로 하며 스테이지 재화는 별도의 런타임 값입니다. 종료 처리 중에는 저장을 막고 조회만 허용합니다.

## 기본 저장과 재실행 복원

1. Play 실행 후 초기화 성공과 초기 조회 확인.
2. 상점/강화에서 검증할 값을 만들고 전체 진행 저장/조회.
3. Play 종료 후 재실행한 초기 조회와 이전 전체 조회 비교.
4. 재화/수량/단계/해금/선택/미션 완료와 지급/최고 별이 유지되는지 확인.

데이터가 빈 항목은 빈 상태 복원까지만 확인한 것입니다. 미션 기록 복원과 실제 전투의 조건 판정 검증은 구분합니다.

## 최고 별

도전 시작·승리 별/점수 입력·정산 조작은 [종료 보상 검증](CURRENCY_TEST.md#종료-보상)을 사용합니다. 여기서는 맵/난이도별 저장 결과를 확인합니다.

| 입력 순서 | 기대 결과 |
| --- | --- |
| 첫 승리 1성 | 최고 1성 |
| 같은 맵/난이도 승리 3성 | 최고 3성으로 갱신 |
| 이후 2성 또는 3성 | 최고 3성 유지 |
| 이후 패배/포기 | 기존 기록 유지 |
| 다른 난이도에서 승리 | 원래 난이도와 별도 기록 |
| Play 재실행 | 각 기록 복원 |

난이도 선택은 다음 도전부터 적용됩니다. 최고값 유지와 불필요한 파일 쓰기 생략은 구분해 확인합니다.

## 클리어 최고 점수

위 공통 조작으로 정산한 뒤 최고 점수·점수 기록 여부를 확인합니다.

| 검증 | 기대 결과 |
| --- | --- |
| 점수 필드가 없던 기록 불러오기 | 최고 별 유지, 점수 미기록 |
| 첫 클리어 0점 | 정상 점수 기록으로 구분 |
| 기존보다 낮은 별·높은 점수 / 높은 별·낮은 점수 | 별·점수 최고값을 각각 유지·갱신 |
| 같은 기록·낮은 기록 / 패배·포기 | 기존 최고 기록 유지 |
| 다른 맵·난이도와 재실행 | 기록 분리·복원 |
| 클리어 점수 미전달 / 패배·포기에 점수 전달 | 완료 접수 거절, 잘못된 기록 저장 안 함 |
| 저장 실패 후 재시도 | 접수한 원래 결과·점수 유지, 보상 중복 없음 |

실제 확인 범위는 [완료 이력](../../DONE.md), 남은 저장 호환·실패 검증은 [후속 작업](../../TODO.md#클리어-점수-보상-연결)을 참조합니다.

## 삭제와 신규 생성

1. 전체 종료가 끝난 상태에서 진행 관리의 저장 데이터 삭제 요청.
2. 진행 보유/씬 초기화 해제와 본 파일/백업/임시 파일 제거 확인.
3. 같은 Play 안에서 파일이 자동으로 재생성되지 않는지 확인.
4. 진행 시작 및 씬 연결 요청 후 최초 재화/빈 기록/무기 미선택 확인.
5. Play 재실행 후 신규 진행 복원 확인.

TestScene.Start는 진행이 없으면 시작을 요청하므로 Play를 재실행한 뒤 신규 파일이 생기는 것은 정상입니다. 삭제 직후 미생성은 같은 Play 안에서 확인합니다.

## 파일 실패와 버전

- 실제 쓰기 실패: 초기화 후 본 파일 옆에 `slot_0.json.tmp`라는 빈 폴더를 만들어 쓰기를 막고 전체 진행 저장 실패/원본 유지 확인. 만든 폴더를 제거하고 다시 저장해 성공 확인. 원본 파일을 폴더로 바꾸지 않습니다.
- 종료 재시도: 저장할 새 기록이 있는 도전에서 쓰기를 막고 종료 대기/실패 위치 확인. 방해 폴더 제거 후 저장/정산은 실패한 종료 단계 재시도, 정리는 남은 정리 버튼 사용. 이미 성공한 보상을 반복하지 않아야 합니다.
- 버전 변환: 격리 파일의 6→8 변환을 확인했습니다. 실제 이전 플레이 파일의 전체 기록 회귀는 복사본으로 별도 확인합니다.
- 손상/미지원 버전: 보관한 복사본으로 검사하고 초기화 실패/원본 미덮어쓰기 확인. `.bak` 자동 복구를 기대하지 않습니다.
- 삭제 실패 후 재연결과 이동 전 미저장 처리/쓰기 생략은 별도 확인이 필요합니다. 현재 Inspector에는 TrySavePendingProgress 전용 검증 버튼이 없습니다.

## 진행 JSON 구조·복원 검증

Play 중 초기화된 SaveManager Inspector에서 `진행 JSON 구조·복원 검증 (격리된 테스트 파일)`을 실행합니다. SaveJsonDebug는 고유 임시 폴더·새 서비스·런타임 재화 설정을 사용하고 종료 시 정리합니다. 실제 저장 진행·사용자 파일·Firebase 서버는 변경하지 않습니다.

아래는 2026-10-28 버전 7 기준 사용자 확인 이력(**20/20 통과**)입니다. 개편 후 버전 8 결과는 [현재 확인](#2026-10-30-저장소-분리-확인)에 둡니다.

| 검증 | 확인 결과 |
| --- | --- |
| 버전 7 정상 빈 목록/필수 목록 누락·null·타입 오류 | 정상 허용/손상 InvalidData |
| 버전 6→7/기존 필수 목록 누락/미지원 버전 | 기록 보존·변환 저장/InvalidData/UnsupportedVersion |
| 백업 메타데이터 버전 불일치·손상 내부 JSON·손상 보관본 | 호환 검사 전 거절, 현재 진행·원본 유지 |
| 정상 내부 JSON 복원 | 새 진행 확정·이전 원본 보관 |

클라우드 내부 JSON은 SaveService 복원 경로 검증이며 실제 인증/통신을 거치지 않습니다. 단축키 파일 검증은 [INPUT_SYSTEM](../INPUT_SYSTEM.md#확인-범위)에서 관리합니다.

## Firebase 설정과 화면 연결

2026-10-27 사용자 설정과 Unity Editor 검증으로 익명 인증·Firestore 생성·규칙 적용, 검증용 SaveManager 연결을 확인했습니다. SaveManagerEditor의 Inspector 도구를 사용했으며 실제 설정 UI·씬 이동 연결 완료와 구분합니다. 아래는 설정/연결 기준입니다.

1. Firebase Console에서 사용할 프로젝트를 선택하고 프로젝트 ID/웹 API 키 확인. 서비스 계정 비공개 키는 클라이언트나 저장소에 넣지 않습니다.
2. Authentication의 로그인 제공업체에서 익명 인증 활성화. Firestore Database의 `(default)` 데이터베이스 생성.
3. Firestore 규칙에 프로젝트 루트의 `Firebase/firestore.rules` 적용. 테스트용 전체 허용 규칙을 사용하지 않습니다.
4. 공통 프리팹의 SaveManager에 프로젝트 ID/API 키와 강화/미션 데이터 맵 연결. 기존 CurrencyData를 유지하고 씬의 별도 관리자 배치는 정리.
5. 타이틀·결과 설정은 [화면별 요청 경로](../../LJ_INTEGRATION_GUIDE.md#수동-백업복원-연결)를 사용합니다. TestScene은 Start에서 진행 사용권을 연결하므로 Auto Begin Stage를 꺼도 Inspector의 직접 백업 요청을 사용할 수 없습니다.

### Inspector 검증 도구

BackupTest에서 Play 중 자동 생성된 GameManager의 SaveManager를 선택합니다. TestScene이 진행을 사용하지 않는 구성이며 Firebase 설정과 강화/미션 맵은 Play 전에 공통 프리팹에 연결합니다. Inspector는 GameManager가 소유한 초기화된 관리자에서 사용하며 런타임 설정/API와 씬을 도구가 변경하지 않습니다.

| 버튼 | 역할 |
| --- | --- |
| 로컬 진행 불러오기 / 현재 확정 저장값 조회 | 확정 진행이 없을 때 기존 파일로 준비 / 파일 읽기 없이 확정 진행 복사본 JSON 표시 |
| 클라우드 백업 요청 | 최초 백업은 바로 업로드, 기존 백업은 확인 대기 |
| 백업 덮어쓰기 승인 / 취소 | 준비한 후보로 서버 교체 / 후보 해제·서버 유지 |
| 클라우드 불러오기 | 확인 팝업 승인 후 서버 백업을 검사·로컬 저장·공유 진행에 적용 |
| 복원 직전 로컬 진행으로 복구 | 확인 후 로컬 보관본으로 복구. 서버 시각이 없는 성공 결과가 정상 |

진행이 이미 준비되어 있으면 로컬 진행 불러오기는 파일을 다시 읽지 않고 Success를 반환합니다. 외부에서 바꾼 파일의 재읽기 확인은 Play 종료 후 재실행으로 구분합니다.

백업 요청·확인 대기 중 다른 진행 변경을 막고, 완료 후 확정 진행과 결과를 다시 확인합니다.

## Firebase 검증 절차

기존 백업을 A, 변경한 로컬 진행을 B로 구분합니다. 기본 백업·복원의 사용자 확인 이력은 [DONE](../../DONE.md)을 참조합니다.

| 기본 검증 | 기대 결과 |
| --- | --- |
| 최초 백업 | Success와 서버 시각 반환, Firestore 문서 생성 확인 |
| 변경한 로컬 B에서 클라우드 A 복원 | Success, 재화·아이템·도감 해금/신규·선택 무기가 A로 복원되고 나머지 저장 항목도 일치 |
| Play 종료/재실행 후 적용 | PlayerTest 초기/전체 저장값 조회가 A와 일치. 로컬 파일 저장과 재실행 적용 확인 |
| 복원 전 보관본 복구 | B로 정상 복구, 강화·미션·해금·최고 별도 유지 |
| 백업 덮어쓰기 취소/승인 | ConfirmationRequired → 취소 성공 → 다음 조회 시 기존 서버 시각 유지. 재요청·승인 후 Success와 갱신된 서버 시각 확인 |
| 오프라인 실패/재연결 | NetworkFailed·Request timeout 반환, 사용자 보고로 로컬 값 유지 확인. 재연결 후 같은 백업 시각으로 불러오기 Success |
| 재실행 후 기존 백업 접근 | 사용자 보고로 반복 확인. 기존 익명 사용자 백업 접근 유지 |

### 실패·경합 검증

비교할 저장 항목과 복사본을 확보하고, 인증 정보 유실은 복구 가능한 시험 환경에서 다룹니다. 실행 상태는 [백업 TODO](../../TODO.md#firebase-수동-백업복원)를 참조합니다.

| 조작 | 기대 결과 |
| --- | --- |
| 확인 대기 중 서버 문서 변경 | 승인 시 PreconditionFailed로 교체 거절 |
| 클라우드 복원 확인 팝업 취소 | 기존 로컬 유지 |
| 서버 백업 없이 복원 | NoCloudBackup 안내, 기존 로컬 유지 |
| 인증 거절/업로드 실패·저장 여부 불확실 응답 | 단계에 맞는 실패 반환, 업로드 반영 불확실은 UploadUnconfirmed로 구분. 오프라인 다운로드 실패 확인과 구분 |
| 실제 서버 응답의 손상 JSON/버전 불일치·미지원/크기 초과/강화·미션 설정 불일치 | 로컬 파일 교체 전에 거절, 기존 진행 유지. 내부 JSON 서비스 검증은 위 별도 결과 참조 |
| 원본 보존 또는 로컬 쓰기 실패 후 복원 재시도 | 실패 시 기존 파일/메모리 진행 유지, 원인 제거 후 명시적 재시도 가능 |
| 버튼 연속 입력/확인 대기 중 시작·삭제·씬 연결/요청 중 종료 | 중복·충돌 요청 거절, 종료 후 응답으로 파일 교체나 후보 재생성하지 않음 |
| 인증 보관 실패/보관 정보 유실 | 보관 실패는 성공 처리하지 않음. 정보 유실 후 이전 UID 복원이 자동 보장되지 않음을 확인 |
| 일반 로컬 플레이를 오프라인에서 수행 | 백업 인증/통신 없이 기존 로컬 저장 사용 |

보안 규칙은 별도 Emulator 시험 환경을 구성해 미인증/다른 UID/잘못된 슬롯·필드·버전·크기를 거절하고 자기 UID의 정상 조회/작성을 허용하는지 확인합니다. 규칙 테스트 구성과 실행은 미수행이며 현재 REST 주소는 실제 Firebase 서버를 사용합니다.

### 결과 화면 통합 검증

[정식 씬과 화면 연결](../../LJ_INTEGRATION_GUIDE.md#수동-백업복원-연결) 후 로비에서 Stage 1에 입장합니다. 승리 또는 패배 후 저장·정산·정리가 끝날 때까지 백업 버튼이 비활성화되어 있는지 확인하고 아래 절차를 진행합니다.

| 조작 | 기대 결과 |
| --- | --- |
| 기존 백업 교체 요청 → 취소 또는 승인 | 확인 대기 중 중복 요청·씬 이동 차단. 취소 시 서버 백업 유지, 승인 시 서버 시각 갱신. 두 경우 모두 기존 결과 화면의 진행 사용 재개 |
| 미저장 진행 저장 실패 또는 Firebase 복원 실패 | 기존 진행과 결과 유지. 원인 해소 후 결과 화면에서 재요청 가능 |
| 다른 값의 백업 복원 | 로컬 진행 반영 → 이전 결과 세션 해제 → 타이틀 이동. 새 진행으로 로비에 들어가고 복원 완료 안내는 한 번 표시 |
| 복원 성공 후 타이틀 로드 실패 | `RetryLoad()`로 타이틀 로드만 재시도. 복원·정산 반복 없이 타이틀 도착 후 완료 안내 표시 |

## 종료 보상 저장

영구 재화·맵/난이도별 최고 별/점수·별 지급 이력·최근 정산 기록을 확인합니다. 저장 항목·포기 처리 기준은 [종료 보상 저장 계약](../SAVE_SYSTEM.md#종료-보상-통합-저장), 정상 지급 조작은 [종료 보상 검증](CURRENCY_TEST.md#종료-보상)을 따릅니다.

자동 비교는 저장 검증의 `복원 비교 기준 기록`을 누른 뒤 Play를 중단하고 다시 실행합니다. 기준은 에디터 세션에 보관하며 게임 저장을 추가로 요청하지 않습니다. 재실행 후 최초 불러오기에서 보상 관련 항목을 비교하고 기준을 해제합니다. 일괄 검증 완료가 기준을 자동 기록하지는 않습니다.

실제 확인 범위는 [완료 이력](../../DONE.md#2026-11-05-클리어-보상-설정과-정상-지급-확인), 남은 검증은 [후속 작업](../../TODO.md#클리어-점수-보상-연결)을 참조합니다.
