# AGENT_GUIDE

## PURPOSE

이 문서는 팀 프로젝트에서 AI 에이전트가 작업할 때 따라야 하는 공통 행동 규칙을 정의합니다.

에이전트는 사용자의 요청과 현재 담당 범위를 기준으로 작업하며, 다른 팀원의 작업 영역이나 공용 구조를 임의로 확장 수정하지 않습니다.

## PRIORITY

작업 판단 우선순위는 다음과 같습니다.

1. 사용자의 현재 명시적 요청
2. 현재 작업에 지정된 담당 범위
3. 이 문서의 공통 규칙
4. 프로젝트별 설계 / 구조 / 로드맵 문서
5. 일반적인 코드 개선 판단

사용자의 명시적 지시가 없는 경우 작업 범위를 스스로 확대하지 않습니다.

## WORK_SCOPE

### 허용

- 현재 사용자 요청에 포함된 기능과 파일을 수정합니다.
- 담당 영역 내부에서 필요한 파일을 생성할 수 있습니다.
- 연동 구조, API, 데이터 흐름을 확인하기 위해 다른 담당자의 코드를 읽을 수 있습니다.
- 현재 작업 범위 안에서 필요한 최소한의 수정만 수행합니다.

### 금지

- 다른 담당자의 스크립트나 파일을 임의로 수정하지 않습니다.
- 관련성이 있다는 이유만으로 인접 시스템까지 수정하지 않습니다.
- 요청하지 않은 리팩터링, 구조 변경, 최적화, 네이밍 통일을 수행하지 않습니다.
- 담당 범위 밖의 클래스, 메서드, 필드, 이벤트, 파일명을 임의로 변경하지 않습니다.
- 담당 범위 밖의 파일을 이동하거나 삭제하지 않습니다.
- 공용 인터페이스, 베이스 클래스, Manager, 공용 데이터 구조, 공용 유틸리티의 계약을 임의로 변경하지 않습니다.
- 컴파일 또는 실행 오류를 없애기 위해 다른 담당자의 코드를 임의로 수정하지 않습니다.

다른 파일은 확인을 위해 읽을 수 있지만, **참조 가능과 수정 가능은 동일하지 않습니다.**

## OUT_OF_SCOPE_CHANGE

현재 작업을 완료하기 위해 담당 범위 밖의 변경이 필요하다고 판단한 경우 다음을 따릅니다.

1. 해당 파일을 직접 수정하지 않습니다.
2. 현재 담당 범위 안에서 해결 가능한 방법이 있는지 먼저 검토합니다.
3. 범위 밖 변경이 반드시 필요하면 변경 대상과 이유를 사용자에게 보고합니다.
4. 사용자 승인 없이 작업 범위를 확장하지 않습니다.

외부 코드에서 기존 오류나 설계 문제를 발견해도 현재 요청과 직접 관련되지 않으면 별도 수정하지 않습니다.

## COMMON_CODE

공용 코드의 변경은 여러 작업에 영향을 줄 수 있으므로 특히 제한합니다.

다음과 같은 대상은 담당자가 아니면 임의로 수정하지 않습니다.

- 공용 Manager
- 공용 Interface
- Base Class
- 공용 Model / Data 구조
- 공용 Utility
- 공용 입력 / 저장 / 사운드 / 씬 흐름
- 여러 시스템이 동시에 참조하는 API

공용 계약 변경이 필요한 경우 직접 변경하지 않고 필요한 변경 내용을 보고합니다.

## REFACTORING

현재 기능 구현에 필요하지 않은 개선 작업은 수행하지 않습니다.

다음 작업은 사용자가 별도로 요청한 경우에만 진행합니다.

- 대규모 리팩터링
- 책임 재분배
- 클래스 분리 / 병합
- 폴더 구조 변경
- 네이밍 일괄 변경
- 패턴 도입
- 성능 최적화
- 코드 스타일 일괄 정리
- 기존 구조를 대체하는 신규 아키텍처 도입

기존 구조가 불완전해 보여도 현재 요청을 해결하는 데 필요한 최소 변경을 우선합니다.

## BUILD_AND_EXECUTION

C# 프로젝트 전체 빌드, Unity 실행·플레이 모드·Player Build와 Unity 컴파일을 유도하는 명령은 수행하지 않습니다. 예외는 사용자가 명시적으로 요청하거나 승인한 경우에만 적용합니다.

단순 문법 확인, 코드 검토, 습관적인 검증을 이유로 전체 C# 빌드나 Unity 빌드를 실행하지 않습니다.

빌드 또는 실행 과정에서 현재 담당 범위 밖의 오류가 발견되어도 해당 오류를 해결하기 위해 다른 담당자의 코드를 임의로 수정하지 않습니다.

Unity 직접 실행, 플레이 모드 검증, 프로젝트 빌드 역시 동일한 원칙을 적용합니다.

## UNITY_ASSET_AND_REFERENCE

사용자 요청이나 현재 작업 범위에 포함되지 않은 경우 다음 작업을 임의로 수행하지 않습니다.

- Scene 구조 변경
- Prefab 구조 변경
- Inspector 참조 일괄 변경
- ScriptableObject 데이터 일괄 변경
- .meta 수정
- Unity YAML 직접 수정
- 기존 에셋 삭제 / 이동 / 이름 변경

Unity에서 수동 연결이 필요한 작업은 코드 작업 완료와 구분하여 TODO 또는 사용자 확인 사항으로 남깁니다.

## DOCUMENTATION

코드 수정 승인에 문서 갱신이 자동으로 포함되지는 않습니다. 문서는 사용자가 요청한 범위에서만 수정하며, 완료 내용과 남은 작업을 이해하는 데 필요한 핵심을 기록합니다. 세부 로그나 검사 과정은 누적하지 않습니다.

프로젝트 진행 상태는 문서별 역할을 구분하여 기록합니다.

- `PROJECT_CONTEXT.md`: 게임 목표, 핵심 플레이, 프로젝트 전제
- `ARCHITECTURE.md`: 시스템 구조, 책임, 의존 관계
- `ROADMAP.md`: 주차별 팀 목표와 전체 개발 단계
- `TODO.md`: 현재 남은 구체적인 작업과 검증
- `ERROR.md`: 실제 개발을 막았거나 원인 추적 비용이 컸던 오류
- `DONE.md`: 완료된 변경과 실제 확인 범위
- `System_Guide.md`: 프로젝트 소개와 문서 탐색 색인
- `Systems/PLAY_FLOW.md`: 입장·도전·종료·재시도·씬 이동의 공통 호출 순서와 완료 경계
- `LJ_INTEGRATION_GUIDE.md`: 담당별 연결 대상·현재 연결 상태·남은 연계 요구
- `Systems/COMBAT_SYSTEM.md`: 구현된 공통 전투 API/이벤트/연동 방법
- `Systems/Todo/COMBAT_TODO.md`: 전투 단계별 작업/미확정 사항/남은 검증

시스템 문서에는 사용 계약과 현재 연결 상태를 기록하고, 작업 목록과 검증 예정 항목은 해당 시스템의 TODO에 기록합니다. 공용 TODO는 전체 진행 상태와 상세 문서 링크를 유지하며 DONE은 실제 수행한 변경/검증을 기록합니다. 코딩 스타일은 작업자의 담당 문서를 적용하며 LJ 규칙을 다른 담당자에게 일괄 적용하지 않습니다.

같은 내용을 여러 문서에 중복 기록하지 않고, 상세 내용이 다른 문서의 책임이면 링크로 연결합니다.

시스템 문서에는 자기 기능의 추가 조건만 남기고 전체 플레이 절차는 PLAY_FLOW를 참조합니다. 검증 항목은 기능별 TODO에서 한 번 관리하며 Test 문서는 실행 방법·기대 결과를 제공합니다. 개요·연계 문서에 API 명세와 검증 목록을 복사해 별도 기준을 만들지 않습니다.

## COMPLETION_CHECK

작업 종료 전 다음을 확인합니다.

- 수정한 파일이 현재 담당 범위에 포함되는지 확인합니다.
- 요청하지 않은 파일이 변경되지 않았는지 확인합니다.
- 공용 코드나 다른 담당자의 영역을 임의로 변경하지 않았는지 확인합니다.
- 임의 리팩터링이나 구조 변경이 포함되지 않았는지 확인합니다.
- 코드 반영과 Unity 수동 연결 / 실행 검증을 구분합니다.
- 확인하지 않은 사항을 완료로 기록하지 않습니다.
- 원인이 확정되지 않은 문제를 단정하지 않습니다.
