# LJ_CODING_STYLE

## PURPOSE

이 문서는 LJ 담당 영역에서 AI 에이전트가 코드를 작성하거나 수정할 때 따라야 하는 코딩 스타일을 정의합니다.

기존 프로젝트의 책임 분리, 명명 방식, 상태 처리 순서를 유지하며 스타일 정리만을 이유로 기존 구조를 임의 변경하지 않습니다.

## NAMING

### 클래스/메서드/프로퍼티/이벤트

`PascalCase`를 사용합니다.

```csharp
CharacterMover
TrySetOpen()
IsOpen
OnClosed
```

### private 필드

`_camelCase`를 사용합니다.

```csharp
bool _isOpen;
float _moveSpeed;
```

### 지역 변수/파라미터

`camelCase`를 사용합니다.

```csharp
float moveSpeed;

public bool TrySetOpen ( bool isOpen )
{
}
```

### 인터페이스

`I` 접두사를 사용합니다.

```csharp
IInteractable
IRoomTarget
```

### 이름의 의미

이름은 실제 책임과 행동을 기준으로 정합니다. 참고 코드가 제공되면 같은 책임의 변수명을 그 코드와 유사하게 작성합니다.

- bool 이름은 `is` / `can` / `has` 등으로 의미를 구분합니다. GameManager 변수는 `gameManager` 또는 `gm`을 사용합니다.
- 이름이 길어 역할 파악을 방해하면 짧은 대안을 여러 개 제시하고 임의로 일괄 변경하지 않습니다.
- 한 함수의 `out` 또는 한 이벤트의 인자가 3개 이상이면 책임과 전달 구조를 재검토합니다. 기존 API를 무조건 변경하라는 기준은 아닙니다.

- 모듈 소유 주체는 `_owner`, 실제 피해 발생원은 `_source`로 구분합니다.
- 피해 정보의 `DamageInfo.Attacker`와 실행 정보의 `AttackContext.Attacker`는 실제 공격 주체를 뜻합니다.
- 탐색 위치는 `_detectionCenter`처럼 실제 역할로 명명하며 적중 위치와 혼동하지 않습니다.
- 입력 경로는 `"Player/Move"`, `"Player/Look"`, `"Player/Attack"`처럼 직접 작성합니다. 현재 규모에서 공통 접두사 문자열 조합을 추가하지 않습니다.

- 상태 조회: `IsOpen`, `IsReady`
- 실행 가능 여부: `CanInteract`
- 실패 가능한 실행/결과 획득: `TrySetOpen`, `TryReturn`
- 이벤트 요청 처리: `HandlePurchaseRequested`
- 이벤트: `OnClosed`, `OnAngleChanged`

`Try`는 단순히 bool을 반환한다는 이유만으로 붙이지 않습니다.

## FILE_AND_TYPE

파일명과 주된 클래스명은 일치시키는 것을 기본으로 합니다.

관련 enum, 결과 타입, 보조 데이터처럼 함께 관리하는 것이 자연스러운 타입은 한 파일에 둘 수 있습니다.

단일 타입 파일을 기계적으로 강제하지 않습니다. 공통 전투 enum은 데이터 본문을 쉽게 읽을 수 있도록 별도 파일로 관리합니다.

### 중첩 타입

중첩 클래스는 바깥 타입의 구현에만 속하고 독립적으로 사용할 책임이 없는 경우에 제한적으로 사용합니다. 파일 수를 줄이거나 관련 이름을 묶으려는 이유만으로 중첩하지 않습니다.

- 여러 시스템에서 사용하는 데이터/결과/서비스는 독립 타입을 우선합니다.
- 독립적인 수명이나 동작을 가진 타입은 분리를 검토합니다.
- 여러 단계의 중첩으로 탐색과 책임 파악을 어렵게 만들지 않습니다.
- 같은 파일에 관련 타입을 선언하는 것과 클래스 안에 중첩하는 것은 별개입니다.

## FORMATTING

### 중괄호

여는 중괄호는 다음 줄에 배치합니다.

```csharp
if ( purchased == true )
{
    _save.SaveSupportItems( save );
}
```

### 단일문 조건

한 문장 조건이나 반복 처리에는 중괄호를 생략할 수 있습니다.

```csharp
if ( CanNavigate == false )
    return false;
```

### 공백/줄바꿈

공백, 괄호, 쉼표 형식은 수정 대상과 가까운 기존 스크립트 스타일을 우선합니다.

긴 조건이나 인자 목록은 여러 줄로 나누고, 처리 흐름 사이에는 빈 줄을 둡니다.

기존 파일의 줄바꿈과 인코딩은 가능한 한 유지합니다.

## ACCESS_MODIFIERS

일반 비공개 필드와 일반 비공개 함수의 `private`은 생략합니다.

```csharp
bool _isOpen;

bool CheckCanInteract ()
{
}
```

Unity 호출 함수에는 `private`을 명시합니다.

```csharp
private void Awake ()
{
}

private void Update ()
{
}
```

상속에 필요한 `protected`, `virtual`, `override`는 명시합니다.

제한 키워드는 실제로 보장해야 할 계약이 있을 때 사용하며 관성적으로 붙이지 않습니다.

| 항목 | 사용 판단 기준 |
| --- | --- |
| `internal` | 실제 어셈블리 경계에서 접근을 제한해야 하는가 |
| `sealed` | 상속을 금지해야 하는 구체적인 이유가 있는가 |
| `readonly` | 변경 금지를 코드 계약으로 보장해야 하는가 |
| `readonly struct` | 값 타입이라는 사실 외에 타입 전체의 변경 금지가 필요한가 |
| `static` | 인스턴스 상태와 수명을 소유하지 않는 책임인가 |

현재 상속하지 않거나 생성자에서만 대입한다는 사실만으로 `sealed`나 `readonly`를 자동 적용하지 않습니다. DamageInfo의 readonly struct는 해당 피해 전달 계약에 따른 기존 사례이며 다른 전달 타입에 일괄 적용하는 근거가 아닙니다. 이 기준을 이유로 기존 선언을 요청 없이 일괄 변경하지 않습니다.

## SERIALIZED_FIELDS

Inspector에서 설정하거나 연결할 값은 `[SerializeField]`를 사용합니다.

```csharp
[Header( "----- 이동 -----" )]
[SerializeField] float _moveSpeed;
[SerializeField] Transform _target;
```

관련 설정과 참조는 `[Header( "----- 기능명 -----" )]` 형식으로 묶을 수 있습니다.

직렬화 설정 필드를 모은 뒤 일반 런타임 필드를 배치하고, 필드 선언은 프로퍼티·이벤트·함수 앞에 모읍니다. 기능이 관련되어 있다는 이유로 직렬화 필드 사이에 일반 런타임 필드를 끼우지 않습니다. 선언 위치만 정리할 때는 이름·속성·초기값과 초기화 식의 실행 순서를 유지합니다.

확인용 런타임 값을 Inspector에 표시할 때는 `[SerializeField]`와 `읽기 전용` 헤더로 용도를 안내할 수 있습니다. 헤더는 실제 편집 잠금 기능이 아니며 상태 변경은 해당 모듈의 API로 수행합니다.

`Min`, `Range`, `OnValidate`는 관성적으로 추가하지 않습니다. 실제로 필요한 설정 제약과 처리 함수의 Clamp/검사 책임을 확인한 뒤 사용합니다. 기존 속성을 스타일 정리만으로 제거하지 않습니다.

상위 초기화 코드가 이미 보유한 동일 모듈은 Init 인자로 전달하고 하위 Inspector에 중복 할당하지 않습니다. 필수 참조와 미연결 상태의 검사 기준은 [VALIDATION](#validation)을 따릅니다.

직렬화 필드의 이름을 변경할 때는 기존 씬/프리팹 값의 유지 여부를 확인합니다. 이름 변경만으로 기존 Inspector 값이 보존된다고 가정하지 않습니다.

## PROPERTIES

런타임 상태는 비공개 필드로 보관하고 읽기 프로퍼티로 공개하는 방식을 우선합니다.

```csharp
bool _isOpen;

/// <summary>
/// 열림 여부
/// </summary>
public bool IsOpen => _isOpen;
```

짧은 프로퍼티는 expression body를 사용할 수 있습니다.

자동 구현 프로퍼티를 짧게 작성하는 기본 수단으로 사용하지 않습니다.

- `{ get; }`, `{ get; set; }`, `{ get; private set; }`를 관성적으로 적용하지 않습니다.
- 별도 상태 처리나 직렬화 요구가 없는 단순 데이터 등에서 자동 구현이 적절한지 판단합니다.
- 외부 변경을 막으려는 목적만으로 자동 구현 프로퍼티나 제한 키워드를 일괄 추가하지 않습니다.
- 프로퍼티 조회에 저장/초기화/무거운 처리를 숨기지 않습니다.
- 이 기준을 이유로 기존 프로퍼티를 요청 없이 일괄 변경하지 않습니다.

조건이 길고 독립적인 판단 책임이 있으면 별도 함수로 분리합니다. 해당 조회가 필요한 검사일 때만 작성하며, 내부 함수마다 같은 조회를 반복하는 근거로 사용하지 않습니다.

```csharp
public bool CanInteract => CheckCanInteract( );
```

## XML_DOCUMENTATION

클래스와 일반 함수에는 짧은 한글 XML 설명을 작성합니다. 클래스 summary는 통일 명칭과 책임을 `명칭 - 담당 기능` 형식으로 작성합니다. 공통 전투 모듈 명칭은 [COMBAT_SYSTEM.md](../Systems/COMBAT_SYSTEM.md)의 명칭 표를 기준으로 합니다.

```csharp
/// <summary>
/// 체력 모듈 - 체력 증감과 생명 상태 관리
/// </summary>
```

이벤트 summary에는 인자의 의미를 괄호로 함께 적습니다. 일반 함수 summary에 인자 목록을 덧붙이지 않으며 `<param>`/`<returns>`로 설명합니다.

```csharp
/// <summary>
/// 사망 이벤트(피해 정보)
/// </summary>
public event Action<DamageInfo> OnDied;
```

이미 이름으로 드러나는 의미를 장황하게 반복하지 않습니다. 코드의 서머리/주석에서 병렬 기능은 쉼표 또는 `타격/종료`처럼 양쪽 공백 없는 `/`로 연결하며 가운데점은 사용하지 않습니다. 이 규칙을 이유로 Markdown 본문의 문장부호를 일괄 치환하지 않습니다.

```csharp
/// <summary>
/// 요청한 개폐 상태로 변경
/// </summary>
/// <param name="isOpen">변경할 열림 여부</param>
/// <returns>실제 상태 변경 여부</returns>
public bool TrySetOpen ( bool isOpen )
{
}
```

규칙:

- `<summary>`는 여는 태그, 설명, 닫는 태그를 각각 별도 줄에 작성합니다.
- 파라미터는 `<param>`으로 설명합니다.
- 반환값이 있는 일반 함수는 `<returns>`를 작성합니다.
- `ref`, `out` 파라미터도 각각 설명합니다.
- Unity 호출 함수에는 XML summary를 강제하지 않습니다.
- 이름과 타입만으로 알 수 있는 내용을 장황하게 반복하지 않습니다.

## COMMENTS

모든 멤버 변수에는 역할을 바로 파악할 수 있는 짧은 한글 설명을 작성합니다.

```csharp
bool _isOpen;        //열림 여부
```

주요 함수에는 검사/상태 변경/실행/이벤트 발행의 흐름과 순서가 필요한 이유를 설명합니다. 코드 자체로 명확한 한 줄마다 같은 내용을 반복하지 않습니다.

함수 사이의 요청/알림 흐름과 상태를 바꾸는 이유를 설명합니다. 시작/실행/완료/복귀/취소처럼 의미가 다른 단계는 구분하고, 변수명이나 바로 아래 코드를 번역한 주석은 늘리지 않습니다.

```csharp
//비활성화 콜백보다 먼저 대여 기록 해제
```

enum 항목이나 의미가 바로 드러나지 않는 지역 변수에도 짧은 설명을 사용할 수 있습니다.

## MEMBER_ORDER

기본적인 멤버 배치는 다음 흐름을 따릅니다.

1. 필드/프로퍼티/이벤트
2. 초기화/구독
3. 프레임 진행
4. 입력/이벤트 핸들
5. 기능 처리
6. 공통 검사/조회

기능 전용 검사와 계산은 해당 기능의 하단에 둡니다. `OnDisable`은 클래스 하단에 두고 기즈모 함수가 있으면 그 아래 최하단에 둡니다. 배치는 가독성 규칙이며 Unity 생명주기 실행 순서를 바꾸지 않습니다. 기존 파일을 배치 통일만을 위해 일괄 재정렬하지 않습니다.

## REGION

`#region`은 긴 클래스에서 연속된 기능 흐름을 묶을 때만 사용합니다.

```csharp
#region ----- 회전 -----

//회전 관련 기능

#endregion
```

함수 한두 개마다 region을 만들지 않습니다.

짧은 클래스에는 region을 사용하지 않아도 됩니다.

## BOOLEAN_CONDITIONS

조건문에서는 bool을 명시적으로 비교합니다.

```csharp
if ( _isReady == false )
    return;

if ( isOpen == true )
{
}
```

bool 값을 반환하거나 대입하는 표현까지 억지로 `== true`/`== false`로 바꾸지 않습니다.

## CONTROL_FLOW

필요한 진입점 검사는 실패 조건에서 `return` 또는 `continue`로 빠져나오는 방식을 우선합니다. 모든 함수에 검사를 추가하라는 의미는 아니며 검사 필요성은 [VALIDATION](#validation)을 따릅니다.

```csharp
if ( CanInteract == false )
    return false;
```

성공한 경우에는 다음 순서를 명확하게 유지합니다.

```text
필요한 진입점 검사
→ 실제 상태/동작 적용
→ 내부 상태 반영
→ 이벤트 알림
```

이벤트를 먼저 보내거나 실제 적용 전 상태를 완료된 것처럼 변경하지 않습니다.

저장 성공 후 적용해야 하는 작업처럼 연계 계약이 정한 선후 관계를 먼저 확인합니다. 비동기 요청 접수와 실제 완료의 구분은 [INITIALIZATION_AND_LIFETIME](#initialization_and_lifetime)을 따릅니다.

## VALIDATION

검사를 추가하기 전에 실제 실패 경로, 검사 책임이 있는 위치, 상위에서 이미 보장한 조건인지 확인합니다. 정상 흐름에서 보장된 값은 내부 호출에서 그대로 사용하며 검사로 잘못된 연결이나 호출 순서를 숨기지 않습니다.

- 파일/사용자 입력 같은 외부 입력, 게임 규칙, 객체 수명에 필요한 검사를 해당 책임이 있는 진입점에 둡니다.
- 이미 검증하거나 내부에서 확정한 값을 하위 함수마다 다시 검사하지 않습니다. 서로 독립적인 외부 진입점은 필요한 검사를 공유할 수 있습니다.
- 생성자나 초기화에서 반드시 연결되는 객체에 반복적인 null 검사/로그/조기 반환을 넣지 않습니다.
- 실질적으로 발생 경로가 없는 무한대/NaN/범위 검사를 추가하지 않습니다. 외부 파일 변환 등 실제 필요한 검사는 유지합니다.
- 재화 부족, 사망 중복, 공격 회차, 중복 피해, 실행 수명처럼 실제 규칙을 보장하는 검사는 유지합니다.
- 종료 후 참조 해제, 탐색 대상 소멸, 연결 중 호출되는 Editor 기즈모처럼 값이 없을 수 있는 정상 경로는 필수 연결 오류와 구분합니다.
- 잘못된 값이나 연결을 임의 기본값/Clamp/무시 처리로 숨기지 않습니다. 기능 계약에서 정한 최초 실행 기본값이나 복원 실패 처리와는 구분합니다.

Unity 객체의 파괴 여부를 확인해야 할 때는 Unity null 비교를 사용합니다.

## FAILURE_AND_CLEANUP

정상 처리 순서를 명확하게 작성하고 실제 필요한 실패 처리만 둡니다. `try`를 함수의 기본 틀로 사용하지 않습니다.

- `try/catch`는 파일 I/O/JSON 해석 등 실제 예외 발생 작업과 실패로 전달하거나 처리할 수 있는 예외 종류에 한정합니다.
- 예외를 처리하는 책임을 한 곳에 두고, 하위에서 이미 결과로 전달한 실패를 상위에서 다시 감싸지 않습니다.
- 정상적인 요청 거절에 매번 `throw`를 추가하지 않습니다. 기존 반환값/결과 계약으로 표현할 수 있는지 먼저 확인합니다.
- 포괄적인 `catch`, 빈 `catch`, 실패를 성공처럼 표시하는 대체 동작으로 구현 오류를 숨기지 않습니다.
- `try/finally`는 예외 발생 시에도 반드시 해제해야 하는 자원/상태가 구체적으로 있을 때만 최소 범위에 둡니다. 이를 사용하기 위해 별도 상태 플래그를 만들지 않습니다.
- 중첩 `try/finally`나 부모/자식의 중복 정리로 오류 이후 처리를 무조건 계속하지 않습니다.
- 이벤트 구독자별 예외 보호 함수나 전역 예외 처리 계층을 관성적으로 만들지 않습니다.
- 실제 기능 요구가 없는 자동 재시도/재진입 차단 플래그/요청 큐를 추가하지 않습니다.

실패 후 유지/복구할 상태와 재시도 주체는 기능 계약으로 정하며, 검사/예외 처리 때문에 핵심 흐름이 묻히지 않도록 합니다.

## INITIALIZATION_AND_LIFETIME

생성/의존성 연결 → 초기화 → 시작/사용 → 종료/해제 순서와 각 단계의 소유자를 명확히 합니다.

- 연계 시스템의 초기화/시작/종료 순서는 소유자가 조율합니다. 함수 배치나 보장되지 않은 Unity 콜백 순서에 의존하지 않습니다.
- 다른 시스템을 호출하기 전에 대상의 필요한 초기화를 완료합니다. 초기화 상태의 검사 기준은 [VALIDATION](#validation)을 따릅니다.
- 씬 재활성화/도전 재시작과 시스템 전체 초기화를 구분합니다. `OnEnable`만으로 전체 상태나 누적 기록을 초기화하지 않습니다.
- 종료 시 새 요청/저장/이벤트를 발생시켜도 되는지 확인하며, 정리 과정이 새 동작을 시작하지 않도록 합니다. 필수 저장은 정해진 종료 절차에서 처리하고 파괴 콜백에 맡기지 않습니다.
- 반복 종료가 실제 가능한 구조인지 확인하고 필요한 소유 경계에서 처리합니다. 모든 하위 객체에 중복 종료 플래그를 붙이지 않습니다.
- 비동기 작업의 요청 접수와 실제 완료를 구분합니다. 반환값/조회 상태/이벤트가 어느 단계를 의미하는지 명확히 하고, 후속 시스템은 필요한 완료 조건 이후 호출합니다.

## EVENT_LIFETIME

이벤트 구독과 해제는 구독자의 실제 사용 수명에 맞춰 짝을 맞춥니다. 아래는 활성 상태 동안 사용하는 구독의 예시이며, 초기화/Dispose 수명이 필요한 구독까지 `OnEnable`/`OnDisable`로 일괄 옮기지 않습니다.

```csharp
private void OnEnable ()
{
    _view.OnRequested += HandleRequested;
}

private void OnDisable ()
{
    _view.OnRequested -= HandleRequested;
}
```

구독 후 현재 상태를 최초 조회해야 하는지 확인합니다. 종료 중에는 계약에 따라 구독을 해제하거나 이벤트 참조를 무알림 정리하며, 전체 초기화/종료 순서는 [INITIALIZATION_AND_LIFETIME](#initialization_and_lifetime)을 따릅니다.

## ARCHITECTURE_STYLE

책임은 다음 기준으로 구분합니다.

| 역할 | 책임 |
| --- | --- |
| SO Data | 설정/튜닝 값 |
| Model | 규칙/판단/런타임 상태 |
| View/실행 모듈 | 실제 표시/동작 적용 |
| Presenter/Controller | 연결/처리 순서 조율 |
| 독립 기능 | 수명과 책임이 명확한 실행/검사/계산 |

접미사를 기계적으로 붙이기보다 실제 책임을 기준으로 분리합니다.

다른 시스템의 Model을 직접 수정하지 않고, 동급 Presenter끼리 직접 상호 의존하는 구조를 만들지 않습니다.

공통 부모는 실제 공유하는 계약과 책임을 기준으로 구성하며 자식 전용 데이터/기능을 공통 부모에 밀어 넣지 않습니다. 예상되는 모든 확장을 위한 범용 구조를 미리 만들지 않습니다.

새 클래스/인터페이스/보조 함수는 분리되는 책임을 설명할 수 있을 때 추가합니다. 기존 코드 복제와 과도한 추상화 사이에서 현재 필요한 수준으로 구현합니다.

### 공통 처리 분리

- 같은 책임과 처리 순서가 반복되면 공통 함수/클래스로 분리합니다.
- 공통 파일 처리/실행 흐름과 기능별 데이터 해석/규칙 검사를 구분해 중복 검사와 예외 처리를 줄입니다.
- 겉모양이 비슷하다는 이유로 서로 다른 규칙을 억지로 통합하지 않습니다.
- 공통화 때문에 인자/분기/설정 플래그가 과도해지면 분리 범위를 재검토합니다.
- 한 줄 전달 함수도 외부 계약 유지/수명 조율 등 역할이 있을 때 사용합니다. 호출 단계를 늘리는 것만을 목적으로 분리하지 않습니다.

## UNITY_STYLE

- 필요한 컴포넌트는 `RequireComponent`와 `GetComponent`를 사용할 수 있습니다.
- Inspector 설정과 런타임 상태를 구분합니다.
- Editor 전용 코드는 `Editor` 폴더 또는 `#if UNITY_EDITOR`로 구분합니다.
- Unity 수동 연결이 필요한 작업과 코드 반영을 동일하게 취급하지 않습니다.

## PRESERVE_EXISTING_STYLE

기존 파일을 수정할 때는 같은 기능/역할의 가까운 참고 스크립트를 우선합니다.

스타일 통일만을 이유로 다음을 대규모 수정하지 않습니다.

- 공백/괄호
- 기존 필드 정렬
- public API
- SerializeField
- 클래스/파일명
- region 구성
- 게임플레이 로직
- 줄바꿈/인코딩

새 코드만 현재 파일의 형식에 자연스럽게 맞춥니다.

## USER_WORK_BOUNDARIES

- 구현 계획이나 코드에 대한 승인은 코드 파일의 생성/수정 범위로만 해석합니다. 계획에 에셋이나 Inspector 연결이 언급돼 있어도 해당 작업의 승인으로 확대 해석하지 않습니다.
- 씬(`.unity`), 프리팹(`.prefab`), 머티리얼(`.mat`), 메타(`.meta`) 등 Unity 에셋은 해당 파일의 생성/수정을 사용자가 별도로 명시적으로 지시한 경우에만 변경합니다. 신규 에셋과 신규 메타 파일 생성도 동일합니다.
- 코드 구현을 위해 필요하다는 이유로 Unity YAML을 직접 작성/수정하거나, GUID를 발급해 참조를 연결하거나, 기존 프리팹/씬의 Inspector 참조를 변경하지 않습니다.
- Unity 에셋 생성/설정과 수동 연결이 필요하면 코드 구현과 구분하여 필요한 작업을 보고합니다. 사용자가 직접 수행할 작업을 에이전트가 임의로 대신하지 않습니다.
- 에이전트는 씬 파일(`.unity`)과 메타 파일(`.meta`)을 삭제하지 않습니다.
- 사용자의 지적이나 문제 보고를 롤백 지시로 해석하지 않습니다. 삭제/복구/롤백은 사용자가 해당 작업을 명시적으로 지시한 경우에만 수행하며 기존 사용자 변경을 보존합니다.
- 스테이징·커밋·푸시는 사용자가 직접 수행하며 에이전트는 실행하지 않습니다.

## WORK_AND_REPORT_RULES

- `TODO.md`와 `DONE.md`는 사용자가 정리를 명시적으로 지시했을 때만 수정합니다. 구현 완료나 수정 승인을 문서 정리 지시로 해석하지 않습니다.
- 변경 보고와 진행 설명은 핵심만 짧게 작성합니다. 상세 설명은 사용자가 요청한 경우에만 작성합니다.
- 사용자의 구현/수정 지시 없이 먼저 파일을 변경하지 않습니다. 확인, 계획 설명, 코드 제시는 실제 파일 수정 승인으로 해석하지 않습니다.
- 수정 지시를 받은 경우에도 요청 범위에 필요한 변경만 수행하고, 별도 개선이나 문서 정리를 임의로 추가하지 않습니다.
- 코드 제안은 수정되는 부분을 먼저 따로 제시하고 필요할 때 전체 코드를 덧붙입니다.
- 기존 코드 변경 제안은 변경 전후를 비교하고, 신규 함수는 책임과 호출 흐름을 설명합니다.
- 공통 API 변경 시 시그니처/호출부/Inspector 연결 영향을 보고합니다. 담당 범위 밖 호출부는 직접 수정하지 않고 필요한 변경을 전달합니다.
- 문서에는 기능/계약/진행 상태/확인 범위를 중심으로 기록합니다. 개별 로그 문구/출력 순서 등 자잘한 실행 내역을 상시 문서에 누적하지 않습니다. 실제 오류 원인 추적에 필요한 근거는 ERROR의 역할에 맞게 구분합니다.
- 문서를 작성하거나 정리할 때 컴퓨터 내부 파일·폴더 경로와 Notion 링크를 적지 않습니다. 프로젝트 문서 사이의 상대 링크와 문서 내부 절 이동 링크는 유지하며 필요한 참조에 사용합니다. Notion 자료는 링크 없이 문서명으로 참조합니다.
- 단순 테스트 결과 로그는 해당 테스트 함수에서 처리하며 로그만을 위해 별도 이벤트 구독/핸들러를 늘리지 않습니다. 로그에는 대상과 확인에 필요한 실제 결과값을 표시합니다.

## EDIT_VISIBILITY

구현 및 파일 수정은 Codex의 **"편집했습니다"** 내역에 변경 파일과 diff가 표시되는 방식으로만 수행합니다.

- 파일 생성/수정에는 `apply_patch` 등 편집 내역에 표시되는 도구를 사용합니다.
- PowerShell `Set-Content`, `WriteAllText`, 출력 리다이렉션, 스크립트 파일 쓰기 등 편집 내역에 표시되지 않는 방식으로 구현하거나 수정하지 않습니다.
- 최종 답변에 변경 파일을 나열하는 것으로 편집 내역 표시를 대신하지 않습니다.
- 이 규칙은 코드뿐 아니라 문서 등 LJ 작업 범위의 파일 변경에도 적용합니다.

## CHECKLIST

코드 작성 또는 수정 후 다음을 확인합니다.

- 이름이 실제 책임을 나타내는가
- 클래스/메서드/프로퍼티/이벤트가 `PascalCase`인가
- private 필드가 `_camelCase`인가
- 지역 변수/파라미터가 `camelCase`인가
- 일반 private과 Unity 호출 함수의 접근 제한자 규칙을 지켰는가
- `internal`/`sealed`/`readonly` 등 제한 키워드와 자동 구현 프로퍼티에 구체적인 사용 근거가 있는가
- 중첩 타입과 파일 분리가 실제 책임에 맞는가
- XML summary/param/returns가 필요한 곳에 작성되었는가
- bool 조건을 명시적으로 비교했는가
- 실패 조건을 먼저 처리해 흐름이 단순한가
- 실제 적용과 상태 반영, 이벤트 알림 순서가 올바른가
- 이벤트 구독과 해제가 짝을 이루는가
- 연계 시스템의 준비/사용/종료 순서와 비동기 요청/완료 구분이 명확한가
- 조기 반환/예외에서도 필요한 상태가 정리되는가
- 실제 발생 경로나 게임 규칙으로 설명하기 어려운 검사, 상하위 중복 검사가 없는가
- 필수 연결 오류를 숨기는 조기 반환이나 대체 동작이 없는가
- 중첩 예외 처리나 부모/자식의 중복 정리로 흐름이 복잡해지지 않았는가
- `try`/`throw`/상태 플래그를 실제 필요 없이 추가하지 않았는가
- 주석이 상태 변경 순서와 함수 사이의 흐름을 설명하는가
- 공통 계약에 자식 전용 책임이나 불필요한 미래 확장을 넣지 않았는가
- 같은 책임의 반복 처리를 공통화하되 기능별 규칙까지 억지로 합치지 않았는가
- 불필요한 Rename, 추상화, 구조 변경을 섞지 않았는가
- 구현/수정한 파일과 diff가 "편집했습니다" 내역에 표시되는 방식으로 작업했는가
